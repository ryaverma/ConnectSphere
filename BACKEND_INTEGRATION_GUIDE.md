# ConnectSphere — Backend Integration & Agent Architecture Specification

**Stack: Node.js + Express · Python + FastAPI + LangGraph · Redis · MongoDB · Neo4j · Pinecone**

**Use Dummy Data for 50 users - Important**

---

## 1. Architecture Overview

ConnectSphere runs on a dual-service backend architecture where two independently deployed services collaborate through a shared Redis layer. The first service is a Node.js/Express application that owns all HTTP API endpoints, JWT authentication, OAuth flows, WebSocket connections, and real-time client communication. The second service is a Python/FastAPI application that owns all LangGraph and LangChain agent pipelines, sentence-transformer embeddings, Neo4j graph algorithm execution, and Celery background workers. These two services never call each other's databases directly — they communicate exclusively through Redis pub/sub events and a shared MongoDB instance. Redis acts simultaneously as the event bus, job queue broker for Celery, response cache with TTL-based expiry, WebSocket session store, and rate limit counter store. MongoDB serves as the primary data store for all application entities. Neo4j serves as the secondary graph database storing the relationship knowledge graph, running PageRank, community detection, and shortest-path algorithms on contact networks. Pinecone stores vector embeddings for contacts, events, and messages, enabling semantic similarity search across the platform.

The request lifecycle for agent-backed operations works as follows. A user action triggers a REST call to Node.js. Node.js validates the request, persists any necessary records to MongoDB, then publishes a Redis pub/sub event with a structured payload. It immediately returns a `job_id` to the frontend. The Python Celery worker subscribed to that Redis channel picks up the event, runs the appropriate LangGraph pipeline, writes the result to MongoDB's `agent_jobs` collection, updates any relevant domain collections (contacts, messages, campaign_contacts, etc.), then publishes a completion event back to Redis. Node.js picks up the completion event via its Redis subscriber and pushes a WebSocket message to the connected client. The frontend, which has been either polling `GET /api/jobs/:job_id` or listening on the WebSocket channel, receives the update and re-renders accordingly. The only exception to this async pattern is the Privacy & Compliance Agent, which is called synchronously via an internal HTTP request from Node.js to Python FastAPI at `POST /internal/compliance/check` before every message send operation. This call must complete within 600ms or Node.js fails open with a logged warning.

Every agent, whether async or sync, produces a standardised response envelope stored in `agent_jobs`: `{ agent_name, job_id, status, output, explanation, evidence[], confidence, errors[], duration_ms, timestamp }`. This envelope is the contract between the Python agent layer and the Node.js API layer. Node.js reads the `output` field to serve data to clients and the `explanation` plus `evidence[]` fields to populate the UI's transparency features like the "Why they matter to you" block and the "Evidence used to personalize this message" section.

## 2. MongoDB Schema

MongoDB replaces PostgreSQL as the primary relational store. All data integrity that would have been enforced by foreign key constraints in PostgreSQL is enforced at the application layer in both Node.js and Python services. Mongoose is the recommended ODM for Node.js. Motor is the recommended async driver for Python. All collections use ObjectId as `_id`. Timestamps (`createdAt`, `updatedAt`) are managed via Mongoose's `timestamps: true` option.

### users

The users collection stores all account information. Fields include `_id` (ObjectId), `email` (String, unique, required, indexed), `password_hash` (String, null if OAuth-only user), `name` (String, required), `title`, `company`, `location`, `initials`, `avatar_color`, `avatar_url`, `bio`, `education`, `linkedin_url`, `github_url`, `twitter_url` (all String), `skills` (String array), `interests` (String array), `goal` (String, the user's primary networking goal text — consumed directly by the Opportunity Detection Agent and Event Recommender Agent), `onboarding_completed` (Boolean, default false), `onboarding_step` (Number, default 1), `email_verified` (Boolean, default false), `subscription_tier` (String, default "free"), `subscription_status` (String, default "active"), `trial_ends_at` (Date), `last_login_at` (Date), `deleted_at` (Date, soft delete), and a nested `settings` subdocument containing all user preferences including `max_messages_per_day` (Number, default 10), `min_days_between_messages` (Number, default 7), `preferred_tone` (String, default "professional"), `notify_new_opportunities` (Boolean), `notify_message_replies` (Boolean), `notify_campaign_updates` (Boolean), `notify_event_reminders` (Boolean), `email_notifications` (Boolean), `push_notifications` (Boolean), `notification_frequency` (String), `ai_message_generation` (Boolean), `auto_schedule_messages` (Boolean), `ai_contact_scoring` (Boolean), `theme` (String), `sidebar_collapsed` (Boolean), `timezone` (String), `locale` (String), `date_format` (String), `profile_visibility` (String), `show_email` (Boolean), and `allow_analytics` (Boolean). Indexes: `email` (unique sparse), `deleted_at`.

## 3. Redis Event Bus — Complete Event Registry

Redis pub/sub is the nervous system connecting Node.js and Python. Node.js publishes all events; Python Celery workers subscribe and trigger agents. The following 18 events form the complete registry.

`contact_imported` is published by Node.js when `POST /api/contacts/bulk-import` or any integration import completes writing raw records to MongoDB. The payload contains `{ user_id, job_id, contact_ids[], source }`. The Profile Parsing Agent subscribes to this event and begins its LangGraph pipeline immediately.

`profiles_enriched` is published by the Profile Parsing Agent on successful completion. Payload: `{ user_id, job_id, contact_ids[], enriched_count }`. The ConnectGraph Builder Agent subscribes and runs its Neo4j node/edge upsert pipeline automatically.

`graph_updated` is published by the ConnectGraph Builder Agent on completion. Payload: `{ user_id, nodes_added, edges_added, graph_metrics }`. The Opportunity Detection Agent subscribes and re-runs opportunity scoring for any active campaigns belonging to this user.

`campaign_created` is published by Node.js after `POST /api/campaigns` persists the new campaign. Payload: `{ user_id, campaign_id, goal_text }`. The Opportunity Detection Agent subscribes and immediately runs its full scoring pipeline for the new campaign.

`campaign_goal_updated` is published by Node.js when `PATCH /api/campaigns/:id` includes a changed `goal` field. Same payload structure as `campaign_created`. Triggers full Opportunity Detection re-rank.

`outreach_requested` is published by Node.js when a single contact is selected for outreach draft generation (from campaign wizard step 2 or contact detail page). Payload: `{ user_id, campaign_id, contact_id, goal_text, tone }`. Outreach Agent subscribes.

`outreach_batch_requested` is published by Node.js when multiple contacts are selected simultaneously in the campaign wizard. Payload: `{ user_id, campaign_id, contact_ids[], goal_text, tone, batch_job_id }`. The Outreach Agent runs as a Celery group task with one sub-task per contact, all reporting back to the parent `batch_job_id`.

`regenerate_draft` is published by Node.js when `POST /api/messages/:id/regenerate` is called. Payload: `{ user_id, message_id, contact_id, campaign_id, tone, variant }`. Outreach Agent re-runs only the message_generation and quality_check nodes for the specified variant.

`message_sent` is published by Node.js after a message is successfully delivered. Payload: `{ user_id, message_id, contact_id, campaign_id, sent_at, send_via }`. Follow-up Lifecycle Agent subscribes and activates the follow-up cadence.

`interaction_received` is published by Node.js when the email reply webhook `POST /webhook/email/incoming` detects a reply to a tracked message. Payload: `{ user_id, message_id, contact_id, thread_id, received_at }`. Follow-up Lifecycle Agent subscribes and cancels any pending follow-up tasks for that contact-campaign pair.

`pre_event_outreach_requested` is published by Node.js when `GET /api/events/:id/pre-outreach` is called. Payload: `{ user_id, event_id }`. Triggers a sequential pipeline: Opportunity Detection Agent runs first to identify contacts likely at the event, then fires `outreach_requested` events for each identified contact to the Outreach Agent.

`events_imported` is published by Node.js after `POST /api/events/import` completes. Payload: `{ user_id, event_ids[] }`. Event Recommender Agent subscribes and re-runs its matching pipeline against the newly imported events.

`daily_reminder_trigger` is a Celery beat scheduled event fired every morning at 8am in the user's local timezone (computed from `users.settings.timezone`). Payload: `{ user_id, as_of_date }`. Follow-up Lifecycle Agent runs its stale relationship scan and reminder creation pipeline.

`contact_stale_check` is a separate daily Celery beat event for the broader sweep of at-risk contacts. Follow-up Lifecycle Agent handles this alongside `daily_reminder_trigger`.

`daily_events_trigger` is a Celery beat event fired every 24 hours. Payload: `{ user_id, date_range }`. Event Recommender Agent re-runs its recommendation pipeline.

`daily_recommendation_trigger` is a Celery beat event fired every 6 hours. Payload: `{ user_id }`. Opportunity Detection Agent re-scores contacts for all active campaigns and updates the Redis cache.

`analytics_refresh_trigger` is a Celery beat event fired every hour. Payload: `{ user_id }`. Analytics Agent runs all MongoDB aggregation pipelines and updates the `analytics_snapshots` collection.

`weekly_insights_trigger` is a Celery beat event fired every Monday at 6am UTC. Payload: `{ user_id }`. Analytics Agent runs its LLM-powered insight generation task and writes results to `analytics_snapshots.insights[]`.

The Redis cache key namespace is also defined here for completeness. `opportunities:{campaign_id}` caches ranked contact lists from Opportunity Detection Agent with a 6-hour TTL. `events:recommendations:{user_id}` caches event recommendations from Event Recommender Agent with a 24-hour TTL. `analytics:{user_id}` caches the latest analytics snapshot with a 1-hour TTL. `graph:{user_id}:nodes` caches serialized graph data for the frontend with a 30-minute TTL. `rate_limit:{user_id}:daily` is a counter that expires at midnight. `session:{jwt_jti}` stores invalidated JWT identifiers for logout with TTL matching the original JWT expiry. `job:status:{job_id}` stores lightweight status strings for polling with a 48-hour TTL.

## 4. Agent Specifications

### Agent 1 — Profile Parsing Agent

The Profile Parsing Agent is a LangGraph stateful pipeline. It subscribes to the `contact_imported` Redis event and processes raw contact data from any source into enriched, normalised, deduplicated MongoDB contact records. It runs asynchronously as a Celery task named `profile_parsing_task`, always returning a job envelope to `agent_jobs`.

The LangGraph pipeline consists of six nodes executed sequentially. The first node, called `normalize`, standardises field names across all four possible sources: `linkedin_csv`, `github`, `gmail`, and `manual`. It maps source-specific field names to the unified contact schema (`name`, `email`, `headline`, `company`, `location`, `connection_date`, `notes`, `mutual_connections`, `source`). It strips company name suffixes like "Inc.", "Ltd.", "Corp." using fuzzy matching to normalise company names for Neo4j graph merging. Missing fields are null-defaulted gracefully. The second node, called `deduplicate`, loads all existing contacts for the `user_id` from MongoDB and checks each incoming record against them. Email exact match is the primary deduplication key. Name fuzzy matching via `python-Levenshtein` with a similarity threshold of 0.85 catches name variations without email data. For fuzzy matches that lack a confirming email, the record is flagged as `potential_duplicate` with a similarity score and surfaced in the frontend for manual review. When merging, the most complete data wins field by field, and all source references are accumulated in the `sources[]` array. The node outputs `{ new_contacts[], updated_contacts[], duplicate_flags[] }`. The third node, called `skill_extraction`, embeds each contact's headline and notes text using `sentence-transformers` with the `all-MiniLM-L6-v2` model. These embeddings are compared against a pre-computed taxonomy of 200+ professional skill embeddings using cosine similarity with a threshold of 0.72. Additionally, `spaCy` noun phrase extraction runs as a fallback keyword matcher for skills not covered by the taxonomy. For GitHub-sourced contacts, repository language arrays, repository descriptions, and README keywords are parsed directly. Each extracted skill is stored with a `confidence` score and a `source` tag of either "embedding", "keyword", or "github". The fourth node, called `strength_score`, computes a 0-100 integer score using the formula: `score = (recency_score * 0.30) + (interaction_count * 0.25) + (mutual_connections * 0.25) + (source_quality * 0.20)`. Recency scores 100 if the connection was made within the last 30 days, then decays by 2 points per week. Interaction count is log-scaled and capped at the equivalent of 100 points. Mutual connections contribute `min(count * 10, 40)` points. Source quality weights are LinkedIn=1.0, Gmail=0.85, GitHub=0.70, Manual=0.50. The fifth node, called `enrichment`, is optional and runs asynchronously within the pipeline. It calls the GitHub REST API for contacts sourced from GitHub to retrieve bio, public_repos count, followers count, and primary languages. It is rate-limited to 10 GitHub API calls per job to avoid hitting secondary rate limits. All enrichment data is stored in `contacts.notes_json`. The sixth node, called `embed_and_store`, generates a final contact bio embedding from the concatenation of headline, skills, and company fields. This embedding is upserted to Pinecone with the `contact_id` as metadata. The enriched contact record is then upserted to MongoDB's contacts collection, and `contact_skills` subdocuments are written. On completion, the agent fires the `profiles_enriched` Redis event.

### Agent 2 — ConnectGraph Builder Agent

The ConnectGraph Builder Agent is a LangChain tool-calling agent with custom Neo4j tools. It subscribes to `profiles_enriched` and runs as a Celery task named `connectgraph_builder_task`. Its sole responsibility is maintaining the Neo4j knowledge graph and syncing graph metrics back to MongoDB.

The agent runs three tasks. The first task, `node_upsert`, processes each enriched contact and upserts the corresponding Neo4j nodes using MERGE operations to avoid duplicates. It creates `(Person)` nodes with properties `contact_id`, `name`, `company`, `title`, `strength_score`, and `embedding_id`. It creates or merges `(Company)` nodes matching on name. It creates or merges `(Topic)` nodes for each extracted skill, matching on name. It then creates edges: `(User)-[:KNOWS { strength_score, since: connection_date, source }]->(Person)` for the direct user-contact relationship, `(Person)-[:WORKS_AT { title, since }]->(Company)` for employment, `(Person)-[:HAS_SKILL { confidence }]->(Topic)` for each skill, and `(Person)-[:KNOWS]->(Person)` for mutual connections when that data is available. The second task, `graph_algorithms`, runs Neo4j Graph Data Science library procedures on the KNOWS subgraph. It runs PageRank to compute influence scores (`Person.pagerank_score`), degree centrality (`Person.degree_centrality`), Louvain community detection (`Person.community_id`), and betweenness centrality for the top 100 nodes only since this is a computationally expensive operation. All computed metrics are stored on Person nodes in Neo4j and synchronised back to `contacts.notes_json` in MongoDB so that the Node.js API can read graph metrics without querying Neo4j directly on every request. The third task, `path_analysis`, computes the shortest path distance from the `User` node to each `Person` node (`graph_distance`: 1 for direct contacts, 2 for friend-of-friend, etc.) and identifies bridge nodes that connect otherwise separate clusters. On completion, the agent fires the `graph_updated` Redis event and publishes a WebSocket `agent:graph_updated` notification to the client.

### Agent 3 — Opportunity Detection Agent

The Opportunity Detection Agent is a LangGraph multi-step pipeline with tool calls. It subscribes to `campaign_created`, `campaign_goal_updated`, `graph_updated` (when active campaigns exist), and `daily_recommendation_trigger`. It runs as a Celery task named `opportunity_detection_task`. Its output — a ranked list of contacts with explainability — is the backbone of the campaign wizard and the Dashboard priority actions widget.

The pipeline has six nodes. The first node, `goal_embedding`, takes the campaign's `goal_text` string and does two things: it generates a vector embedding using `all-MiniLM-L6-v2`, and it calls the LLM to decompose the goal into structured fields `{ target_role, target_companies[], target_skills[], goal_type }` where `goal_type` is one of: job, mentor, collab, event. The decomposed structure is written to `campaigns.goal_decomposition` in MongoDB for use by other agents. The second node, `semantic_retrieval`, queries Pinecone with the goal embedding and retrieves the top-50 contacts for this `user_id` by cosine similarity. This gives a semantically relevant candidate pool. The third node, `graph_scoring`, takes those 50 contacts and fetches their graph metrics from Neo4j (`pagerank_score`, `degree_centrality`, `graph_distance`, `community_id`) and their relationship metrics from MongoDB (`strength_score`, `last_interaction_at`, `interaction_count`). The fourth node, `combined_scoring`, computes a final composite score for each contact using the formula: `final_score = (semantic_similarity * 0.35) + (normalised_strength * 0.25) + (graph_proximity_score * 0.20) + (normalised_pagerank * 0.12) + (recency_score * 0.08)`. The `graph_proximity_score` maps as: 1.0 for direct contacts (distance=1), 0.5 for second-degree (distance=2), and 0.2 for all others. All sub-scores are normalised to [0,1] before combining. The list is sorted descending and the top-k (default 20) are selected. Confidence badges are assigned: high for score > 0.75, medium for score > 0.5, low otherwise. The fifth node, `explainability`, calls the LLM for each of the top-k contacts to generate a 1-2 sentence human-readable explanation of why this person is high-value for the specific goal. The prompt provides the goal text, the contact's role and company, and the evidence signals (mutual connections, shared skills, graph distance, strength score) and instructs the model to be specific and professional. The sixth node, `cache_and_store`, writes the ranked list to Redis at key `opportunities:{campaign_id}` with a 6-hour TTL and upserts individual scores, breakdowns, and explanations to the `campaign_contacts` collection in MongoDB.

### Agent 4 — Outreach Agent

The Outreach Agent is a LangGraph RAG pipeline combined with LLM generation. It subscribes to `outreach_requested`, `outreach_batch_requested`, and `regenerate_draft`. It runs as a Celery task named `outreach_task`, with `outreach_batch_requested` spawning a Celery group of parallel tasks. For each contact, it generates four message variants along with a follow-up cadence schedule.

The pipeline has six nodes. The first node, `context_retrieval`, gathers personalisation context from four sources simultaneously: Pinecone vector search for the top-5 snippets most relevant to both the goal and the contact's profile, MongoDB interactions for the last 3 interactions with this specific contact, Neo4j for mutual connections by name and any shared event attendance, and `contacts.notes_json` for GitHub/LinkedIn enrichment data. These are compiled into a `context_bundle` object. The second node, `personalization_evidence`, analyses the `context_bundle` and extracts the strongest 3-5 personalisation hooks. These hooks are specific pieces of shared context: mutual connections identified by name, shared conferences or events, overlapping or complementary technical skills, recent public activity if available, and shared professional interests. These hooks are stored as the `evidence[]` array that the frontend renders in the "Evidence used to personalize this message" collapsible section. The third node, `message_generation`, makes four LLM calls — one per variant. The SHORT variant targets a maximum of 80 words and includes a subject line. The prompt instructs the model to use 1-2 of the provided hooks, mention exactly how the sender found the contact, include a clear single ask in the last sentence, avoid fake familiarity, and match the requested tone. The LONG variant allows up to 180 words, uses 2-3 hooks, and includes more context about the sender's background. The FOLLOWUP_1 variant, intended for sending if there is no reply after 7 days, is 2-3 sentences, non-pushy, references the original ask, and offers something of value. The FOLLOWUP_2 variant, intended for day 21, is 2 sentences, gracefully closes the loop, and leaves the door open for future contact. The fourth node, `quality_check`, has the LLM evaluate each variant on two boolean criteria (specific personalisation hook present, clear ask present) and a confidence score from 0.0 to 1.0. Any variant scoring below 0.6 is automatically regenerated once before being stored. The fifth node, `cadence_scheduling`, creates the follow-up schedule: the initial message at `now + 1 hour` (or user-specified time), `followup_1` after a configurable delay (default 7 days), and `followup_2` after a further delay (default 14 days). These are written to the messages collection as separate documents with `status: "pending"` and their respective variant enums. The sixth node, `store_drafts`, upserts all four variant documents to MongoDB's messages collection with `status: "pending_approval"`, linking them to the campaign, contact, `evidence[]`, `quality_scores`, and `ai_confidence`. When `regenerate_draft` is the trigger, only the `message_generation` and `quality_check` nodes run for the specified variant, and the existing message document is updated in place.

### Agent 5 — Event Recommender Agent

The Event Recommender Agent is a LangChain tool-calling agent. It subscribes to `daily_events_trigger` and `events_imported`. It runs as a Celery task named `event_recommender_task`. Its output populates the Events page's ranked list and the Dashboard's recommended events widget.

The agent runs five tasks. The first task, `user_profile_embedding`, constructs a user interest vector by embedding the concatenation of the user's goal text, top skills, and recent interaction context descriptions. The second task, `event_embedding`, iterates over all events in the relevant date range that do not yet have a Pinecone embedding. For each, it embeds the concatenation of `name + description + tags` and stores the result in Pinecone with `event_id` as metadata. The third task, `semantic_matching`, queries Pinecone with the user interest vector and retrieves the top-30 events by cosine similarity from the `user_id`-scoped date range. The fourth task, `roi_scoring`, computes an expected ROI score for each of the top-30 events using: `expected_roi = (semantic_relevance * 0.40) + (attendance_quality * 0.30) + (network_overlap * 0.20) + (location_convenience * 0.10)`. Attendance quality is estimated from event type and size metadata. Network overlap is computed via a Neo4j query for contacts who have `HAS_SKILL` topics that overlap with the event's tags, giving a count of likely attendees from the user's existing network. Location convenience is 1.0 for virtual events, 1.0 for events in the user's city, declining with distance. The top-10 are selected. The fifth task, `pre_event_contacts`, runs for each top-10 event to identify which existing contacts are likely to attend based on skill-topic overlap and past attendance patterns. This list is written to `events.predicted_attendees[]` in MongoDB.

### Agent 6 — Follow-up Lifecycle Agent

The Follow-up Lifecycle Agent is a LangChain scheduled tool-calling agent. It subscribes to `message_sent`, `daily_reminder_trigger`, `contact_stale_check`, and `interaction_received`. It runs as a Celery task named `followup_lifecycle_task`. Its output maintains warm relationships and prevents outreach sequences from going stale.

On `message_sent` trigger, the agent runs two tasks. The first, `activate_cadence`, reads the follow-up message records already created by the Outreach Agent's `cadence_scheduling` node and schedules Celery tasks for `followup_1` and `followup_2` to execute at their computed `scheduled_for` times. It updates the initial message's status to "sent" in MongoDB and writes a record to the `interactions` collection with `type: "outreach_sent"`. The second, `response_monitoring_setup`, registers the email thread ID for reply monitoring if `send_via` is "email". When a reply is detected via the `POST /webhook/email/incoming` endpoint and the `interaction_received` event fires, the agent cancels the scheduled follow-up Celery tasks, updates their status to "cancelled" in MongoDB, updates `campaign_contacts.status` to "replied", recalculates `contacts.response_rate`, and fires a WebSocket notification to the user.

On `daily_reminder_trigger` and `contact_stale_check` triggers, the agent runs three tasks. The `stale_relationship_scan` task queries MongoDB for contacts where `last_interaction_at` is more than 90 days ago and `strength_score` is greater than 40, identifying at-risk relationships worth preserving. The `content_suggestion` task calls the LLM for each at-risk contact with a prompt that provides the contact's role, company, relevant skills, and the number of days since last contact, and instructs the model to produce a 1-sentence outreach hook and a relevant article topic suggestion. The `reminder_creation` task writes a document to the `reminders` collection for each at-risk contact, including the hook, content suggestion, priority classification, and a `due_date` of today.

### Agent 7 — Privacy & Compliance Agent

The Privacy & Compliance Agent is a LangChain synchronous validator. Unlike all other agents, it is not triggered by Redis events and does not run as a Celery task. Instead, Node.js makes a direct synchronous HTTP call to `POST /internal/compliance/check` on the Python FastAPI service. This endpoint must respond within 600ms or Node.js logs a warning and fails open (allows the send but flags the message for review). The agent runs four checks in fail-fast order.

Check 1, `rate_limit`, runs a MongoDB count query to determine how many messages the `user_id` has sent in the last 24 hours and compares it against `users.settings.max_messages_per_day`. It also checks whether a message has been sent to this specific `contact_id` within the user's `min_days_between_messages` window. This check takes under 50ms. Check 2, `spam_pattern_detection`, applies rule-based analysis to the message body in under 100ms. It checks for excessive capitalisation (more than 30% of characters), matches against a 50-word spam trigger word list, detects suspicious URLs, flags messages that are too short (fewer than 20 words) or too long (more than 500 words), and runs a Pinecone similarity check to detect duplicate content where the incoming message body is more than 85% similar to any message sent to a different contact in the past 7 days. Check 3, `policy_check`, calls a fast LLM model (claude-haiku or gpt-3.5-turbo) with a prompt asking it to evaluate the message body for: misrepresentation of the sender-recipient relationship, deceptive claims, harassment indicators, and requests for money or personal information. The response is structured JSON with `violation` (boolean), `violation_type` (string or null), and `severity` (1-3). This check only runs if the first two checks pass, keeping average latency under 300ms when needed. Check 4, `consent_verification`, queries MongoDB to verify the contact's `source` field is one of the legitimate import sources and not an unknown or potentially scraped origin. The agent returns `{ approved: boolean, spam_score: 0-100, checks: { rate_limit: {}, spam_pattern: {}, policy: {}, consent: {} }, block_reason: string | null, suggestions: string[] }`. If `approved` is false, Node.js sets `messages.status = "blocked"`, writes the full compliance object to `messages.compliance_check`, and returns HTTP 422 to the frontend with the block reason and suggestions for remediation.

### Agent 8 — Analytics Agent

The Analytics Agent is a LangChain data aggregation agent with an optional LLM component. It subscribes to `analytics_refresh_trigger` (every hour) and `weekly_insights_trigger` (every Monday). It runs as Celery tasks named `analytics_refresh_task` and `analytics_insights_task`. Its output populates every chart, KPI card, and metric on the Analytics page as well as the Dashboard's stat row.

On `analytics_refresh_trigger`, the agent runs four aggregation tasks. The `outreach_metrics` task runs MongoDB aggregation pipelines to compute messages sent, messages replied, response rate, and average response time for the requested date range, then breaks these down by `campaign_id` and by `strength_score` bucket (0-25, 25-50, 50-75, 75-100). The `network_health_metrics` task combines Neo4j graph queries (network density, clustering coefficient) with MongoDB queries (contact counts, industry diversity computed from `contacts.company` field cardinality, reachability score computed as the percentage of target companies from `campaigns.goal_decomposition.target_companies` that have at least one contact path in Neo4j). The `event_roi_metrics` task joins `interactions` with `events` to count new connections made within 14 days of each attended event. The `campaign_funnel` task computes per-campaign conversion rates through each funnel stage: contacts_targeted → drafts_generated → messages_sent → replies_received → goals_achieved. All results are written to a new `analytics_snapshots` document in MongoDB and cached in Redis at `analytics:{user_id}` with a 1-hour TTL.

On `weekly_insights_trigger`, the agent additionally runs the `insight_generation` task, which calls the primary LLM model with a prompt summarising the last 30 days of aggregated metrics and instructing it to generate exactly 3 specific, actionable insights — one about what is working, one about what is not, and one concrete recommendation. These insights are written to `analytics_snapshots.insights[]`.

`POST /api/auth/register` — Creates user in MongoDB, sends verification email via SendGrid, returns JWT access token and refresh token. `POST /api/auth/login` — Validates credentials, updates `last_login_at`, returns tokens. `POST /api/auth/logout` — Writes `jti` to Redis `session:{jti}` with TTL equal to remaining token validity, effectively invalidating the token on all subsequent requests. `POST /api/auth/refresh` — Validates refresh token, issues new access token. `POST /api/auth/forgot-password` and `POST /api/auth/reset-password` — Standard password reset flow via email token. `POST /api/auth/verify-email` — Marks `email_verified: true` in MongoDB. `GET /api/auth/oauth/:provider/authorize` and `GET /api/auth/oauth/:provider/callback` — OAuth 2.0 flows for LinkedIn, GitHub, and Google. ## 6. Background Jobs — Celery Only

All background job processing is handled exclusively by Python Celery workers using Redis as the broker. There is no Bull/BullMQ. The Celery application is configured with Redis as both broker (`CELERY_BROKER_URL=redis://localhost:6379/1`) and result backend (`CELERY_RESULT_BACKEND=redis://localhost:6379/2`), using JSON as the task serializer, a minimum worker concurrency of 4, and a retry policy of maximum 3 retries with exponential backoff (2^n seconds between retries). Failed tasks that exhaust all retries are routed to a dead letter queue for manual inspection.

The agent tasks are: `profile_parsing_task` (triggered by `contact_imported` event), `connectgraph_builder_task` (triggered by `profiles_enriched`), `opportunity_detection_task` (triggered by `campaign_created`, `campaign_goal_updated`, `graph_updated`, `daily_recommendation_trigger`), `outreach_task` (triggered by `outreach_requested`, `regenerate_draft`), `outreach_batch_group` which is a Celery group of parallel `outreach_task` instances triggered by `outreach_batch_requested`, `event_recommender_task` (triggered by `daily_events_trigger`, `events_imported`), `followup_lifecycle_task` (triggered by `message_sent`, `daily_reminder_trigger`, `contact_stale_check`, `interaction_received`), `analytics_refresh_task` (triggered by `analytics_refresh_trigger`), and `analytics_insights_task` (triggered by `weekly_insights_trigger`).

The application-level jobs that previously ran in Bull/BullMQ are migrated to Celery: `send_scheduled_message_task` runs every 5 minutes via Celery beat, queries MongoDB for messages where `scheduled_for <= now` and `status = "scheduled"`, re-runs the Privacy & Compliance Agent check synchronously, and sends via SendGrid if approved. `email_tracking_processor_task` is webhook-triggered: when `POST /api/webhooks/sendgrid` is called, Node.js publishes a `sendgrid_webhook` Redis event and a Celery worker processes the event data, updating message open/click/bounce status in MongoDB. `integration_sync_task` runs every 6 hours per user via Celery beat, iterates over all `user_integrations` with `is_active: true`, calls the respective OAuth APIs to check for new contacts, writes raw records to MongoDB, and publishes `contact_imported` for any new data. `notification_digest_task` runs daily or weekly per user preference via Celery beat, compiles unread notifications from MongoDB, renders an email digest template, and sends via SendGrid. `cleanup_stale_data_task` runs weekly via Celery beat, soft-deletes notifications older than 30 days, and handles any `agent_jobs` that the TTL index has not yet expired. `export_user_data_task` is on-demand, triggered by `POST /api/analytics/export` or the Settings data export button, compiles all user data from MongoDB and Neo4j, generates a ZIP archive, uploads to S3, and emails a presigned URL.

The Celery beat schedule is defined in the Python service configuration file. Key scheduled entries: `daily-recommendation-trigger` runs every 6 hours, `daily-events-trigger` runs every 24 hours, `analytics-refresh-trigger` runs every 1 hour, `weekly-insights-trigger` runs on Mondays at 6am UTC using a crontab schedule, `daily-reminder-trigger` runs daily at 8am per user timezone using a dynamic schedule, `integration-sync` runs every 6 hours, `send-scheduled-messages` runs every 5 minutes, `notification-digest` uses per-user schedules stored in MongoDB, and `cleanup-stale-data` runs weekly on Sundays.

## 7. WebSocket Events

The WebSocket server runs on Node.js using the `ws` library. Multiple Node.js instances share WebSocket state via Redis pub/sub so that agent completion events published by Python workers reach the correct client regardless of which Node instance the client is connected to. On connection, the client sends an `authenticate` message containing the JWT. Node.js validates the token and registers the socket against `ws:user:{user_id}` in Redis.

The following WebSocket events are pushed from server to client. The original spec events are all retained: `notification:new`, `notification:read`, `contact:created`, `contact:updated`, `contact:deleted`, `message:sent`, `message:opened`, `message:replied`, `campaign:updated`, `sync:started`, `sync:completed`.

The following new agent-specific events are added. `agent:job_queued` carries `{ job_id, agent_name, trigger_event }` and fires the moment a Celery task is accepted. `agent:job_started` carries `{ job_id, agent_name }` and fires when the worker begins execution. `agent:job_progress` carries `{ job_id, agent_name, node_name, progress_pct }` and fires at the completion of each LangGraph node, enabling the frontend to show granular step-by-step progress animations (this is what drives the onboarding Step 5 checklist and the campaign wizard loading state). `agent:job_complete` carries `{ job_id, agent_name, status, output_summary }` and fires on success or failure. `agent:contacts_enriched` carries `{ user_id, contact_ids[], enriched_count }` after Profile Parsing Agent completes, prompting the Contacts page to refresh enriched records. `agent:graph_updated` carries `{ user_id, nodes_added, edges_added }` after ConnectGraph Builder Agent completes, prompting the Graph View page to offer a "Graph updated — refresh?" toast. `agent:opportunities_ready` carries `{ user_id, campaign_id, contact_count }` after Opportunity Detection Agent completes, prompting the campaign wizard to advance to the contact selection step. `agent:drafts_ready` carries `{ user_id, contact_id, draft_ids[] }` after Outreach Agent completes for a single contact, prompting the draft editor to populate with generated content. `agent:compliance_blocked` carries `{ user_id, draft_id, block_reason }` after Privacy & Compliance Agent blocks a message, triggering a blocking modal in the outreach UI. `agent:reminders_created` carries `{ user_id, reminder_count }` after Follow-up Lifecycle Agent's daily run, prompting the Dashboard follow-ups widget to refresh.

## 8. Page-by-Page Agent Wiring

### /onboarding

When the user completes Step 3 by uploading a LinkedIn CSV, connecting Gmail, or authenticating GitHub, Node.js writes the raw contact data to MongoDB and immediately publishes the `contact_imported` Redis event with the `job_id` of the resulting Celery task. The Step 5 screen in the frontend receives this `job_id` and begins polling `GET /api/jobs/:job_id`. As the LangGraph pipeline progresses through its nodes, WebSocket `agent:job_progress` events fire, each carrying a `node_name` that maps to one of the progress checklist items ("Importing contacts", "Parsing profiles", "Building your knowledge graph", "Detecting opportunities"). The animated checkmarks appear one by one as each node completes. When `profiles_enriched` fires automatically after Profile Parsing Agent success, ConnectGraph Builder Agent starts and fires its own progress events. The "Your network is ready!" state is triggered when both the `profile_parsing_task` and `connectgraph_builder_task` jobs have `status: "success"`. If the user set a goal in Step 1, an `opportunity_detection_task` also fires silently in the background so that when the user lands on the Dashboard, priority actions are already populated.

### /dashboard

The Dashboard is entirely served from pre-computed data. The KPI stat cards read from the Redis `analytics:{user_id}` cache populated by Analytics Agent. The Priority Actions widget reads from the Redis `opportunities:{campaign_id}` cache for the user's most active campaign. The Upcoming Follow-ups widget reads from `GET /api/reminders?status=pending&limit=5`, which is populated by Follow-up Lifecycle Agent's daily run. The Recommended Events widget reads from Redis `events:recommendations:{user_id}`. On any cache miss for any of these, the relevant agent is triggered asynchronously and the widget shows a skeleton loader until the WebSocket completion event arrives. The Dashboard's WebSocket subscription covers all `agent:*` events for the user so that background updates from any agent result in a toast notification like "Your opportunity list has been updated — refresh?" without forcing a full page reload.

### /contacts

The contact list itself is a pure MongoDB read with no agent involvement. The Import Contacts flow is the main agent trigger point: `POST /api/contacts/bulk-import` publishes `contact_imported` and returns `{ job_id }`. An import progress drawer slides up at the bottom of the Contacts page showing real-time progress via WebSocket `agent:job_progress` events. When import is complete, the contact list auto-refreshes via `agent:contacts_enriched`. Manual contact creation via `POST /api/contacts` also triggers enrichment silently; the contact appears immediately with `strength_score: 0` and the score and skills populate within seconds via a `contact:updated` WebSocket push.

### /contacts/:id

On page load, the "Why they matter to you" explainability block is populated from `campaign_contacts.explanation` (written by Opportunity Detection Agent during the most recent campaign run for any campaign this contact is part of). The graph metrics (PageRank, degree centrality, community membership) in the contact's sidebar are read from `contacts.notes_json` (synced from Neo4j by ConnectGraph Builder Agent). The Graph Neighborhood tab reads directly from Neo4j via `GET /api/network-graph/data?center_contact_id=`. The "Draft Outreach Message" button publishes `outreach_requested` and returns `{ job_id }`. The message editor enters a loading state and populates when `agent:drafts_ready` fires on the WebSocket. If the contact's `notes_json.last_enriched` timestamp is more than 30 days old, Node.js silently publishes `contact_imported` for this single contact on page load, and the enriched data propagates via `contact:updated` without any user-visible interruption.

### /campaigns and /campaigns/:id

Creating a new campaign via the wizard publishes `campaign_created` and returns `{ campaign, job_id }` from the API. The wizard's Step 2 screen enters a loading state with a "Discovering high-value contacts..." message while polling `GET /api/jobs/:job_id`. When the Opportunity Detection Agent completes, `agent:opportunities_ready` fires on the WebSocket and the ranked contact list populates with confidence badges and explainability text. Clicking "Generate Drafts for Selected (N)" publishes `outreach_batch_requested` with a `batch_job_id` and returns individual `job_id` values per contact. The wizard Step 3 shows a per-contact progress list where each row shows "Crafting message..." then "Ready" as individual Outreach Agent tasks complete, each firing `agent:drafts_ready`. Every draft that reaches "Ready" has already been validated by the Privacy & Compliance Agent (called synchronously within the Outreach Agent's store_drafts node as a pre-save check on batch operations). Editing the campaign's goal text inline on the Campaign Detail page and saving triggers `campaign_goal_updated` and re-runs Opportunity Detection, with the updated ranked list appearing after a few seconds.

### /outreach

The draft list on load is a pure MongoDB read. Clicking "Regenerate" for a draft publishes `regenerate_draft` and the editor enters a loading state, streaming-style progress visible via `agent:job_progress`. The draft text populates when `agent:drafts_ready` fires. Clicking "Send Now" calls `POST /api/messages/:id/send`, which synchronously checks with the Privacy & Compliance Agent before returning. If blocked, a blocking compliance modal appears immediately with the specific reason and suggested fixes — no async delay. If approved, the send completes and `message_sent` is published to Redis, where Follow-up Lifecycle Agent activates the cadence in the background. Editing the follow-up cadence timeline writes directly to MongoDB message records; Follow-up Lifecycle Agent reads the updated schedule on its next daily cycle.

### /events

The event list reads from Redis cache on load. The "Get Pre-Event Outreach List" button calls `GET /api/events/:id/pre-outreach`, which publishes `pre_event_outreach_requested` and returns `{ job_id }`. The Opportunity Detection Agent runs first to identify likely attendees, then fires individual `outreach_requested` events for each, and the Outreach Agent generates context-aware messages that mention the shared event. The combined results surface in a panel on the Events page when `agent:job_complete` fires. The "See Who's Attending" modal reads `events.predicted_attendees[]` directly — a pure MongoDB read populated by Event Recommender Agent. No agent runs on modal open.

### /analytics

All data is pre-computed. Every chart reads from `analytics_snapshots` via the respective analytics API routes, all served from Redis cache. The only user-triggered action with any delay is changing the date range, which re-queries MongoDB aggregations directly (fast, no agent re-run needed). The AI Insights section at the bottom of the page reads from `analytics_snapshots.insights[]` and shows the 3 LLM-generated weekly insights with their generation timestamp.

### /settings

The Connected Sources section's "Re-import Data" button publishes `contact_imported` for all contacts of the specified source, with the Profile Parsing Agent's `deduplicate` node performing an incremental diff and skipping contacts enriched within the last 7 days. Rate limit and spam control slider changes write to `users.settings` and are reflected in the Privacy & Compliance Agent's next compliance check without any agent re-run. The "Export all my data" button triggers `export_user_data_task` as a Celery task, and the user receives an email with a presigned S3 download URL when complete. "Delete all data" cascades across MongoDB (all user-owned documents), Neo4j (MATCH (u:User {user_id: $id})-[*]-(n) DETACH DELETE u, n), Pinecone (delete by user_id metadata filter), and Redis (flush all user-namespaced keys), and is logged to `analytics_events` for GDPR audit purposes.

## 10. Migration Strategy

The migration from mock data to the live backend should be executed in the following strict order to minimise risk and enable incremental testing.

Start by provisioning the MongoDB Atlas cluster, Redis instance, and Neo4j database (Docker Compose for local development). Create all MongoDB collections with their indexes. Seed the `subscription_plans` collection and any static data. Next, implement the Node.js authentication layer entirely: the `/api/auth/*` endpoints, JWT middleware, JWT invalidation via Redis, and all three OAuth flows. Replace the AppContext mock user with a real `GET /api/users/me` call and test the full signup-login-logout cycle before touching any other code.

With auth working, implement all core Node.js CRUD routes in priority order: users settings, contacts (all endpoints except bulk-import), campaigns (all except the agent-triggering ones), messages (create/read/update/delete only, not send), events (basic CRUD), and notifications. Replace AppContext's mock data arrays one collection at a time, verifying each page before moving to the next.

After CRUD is stable, set up the Redis event bus infrastructure. Implement the `agent_jobs` MongoDB collection and the `GET /api/jobs/:job_id` polling endpoint with a stub that returns a mocked success after 2 seconds. This lets you build and test the frontend's async polling and WebSocket update flows before the real agents are wired up.

Build the Python FastAPI service skeleton next. Define the Celery application, configure Redis as the broker, write the base agent task structure that reads from Redis, runs a no-op, writes a stub result to `agent_jobs`, and publishes a completion event to Redis. Verify the full Node → Redis → Python → MongoDB → WebSocket pipeline with this stub before writing any real LangGraph code.

Implement agents in this sequence: Profile Parsing Agent first because it is the most foundational (all other agents depend on its output), then ConnectGraph Builder Agent, then Opportunity Detection Agent (unlocks campaign wizard), then Outreach Agent and Privacy & Compliance Agent together (they are tightly coupled through the message send flow), then Follow-up Lifecycle Agent, then Event Recommender Agent, and finally Analytics Agent. Test each agent end-to-end with real data before moving to the next.

After all agents are working individually, wire up the Celery beat schedules for periodic triggers and test the full daily cycle. Finally, implement all third-party OAuth integrations (LinkedIn, GitHub, Google), the SendGrid email delivery and webhook processing, and Stripe billing. Apply feature flags per page when replacing mock data so that partially-migrated pages can coexist with fully-migrated ones without breaking the application.

## 11. Security Considerations

JWT access tokens expire after 15 minutes. Refresh tokens expire after 7 days and are stored as httpOnly cookies. On logout, the JWT `jti` is written to Redis with a TTL matching the remaining token validity, and all subsequent requests with that token are rejected by the JWT middleware even before expiry. All OAuth access tokens stored in `user_integrations` are encrypted at rest using AES-256 before being written to MongoDB. The `INTERNAL_SERVICE_SECRET` environment variable is used as a shared secret on all Node-to-Python internal HTTP calls, validated by FastAPI middleware, so that the `/internal/compliance/check` endpoint is never accessible from outside the private network. MongoDB field-level access control enforces that every query scoped to a `user_id` includes the authenticated user's ID, preventing cross-user data access. All API responses omit `password_hash`, OAuth tokens, and internal metadata fields. Rate limiting at the API level applies 100 requests per minute per `user_id` via a Redis counter, separate from the outreach rate limiting enforced by the Privacy & Compliance Agent. Input validation and sanitisation run on all POST and PATCH bodies via Joi (Node.js) and Pydantic (Python). All file uploads are validated for MIME type and size before being written to S3. CORS is configured to allow only the production frontend origin and localhost in development. HTTPS is enforced in production with HSTS headers. GDPR compliance is maintained through the data export and deletion flows, with all deletion actions logged to `analytics_events` with a `type: "data_deletion"` for audit purposes.
